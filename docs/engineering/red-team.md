## What it does

`red-team` conducts an adversarial security review of a feature [spec](https://www.aihero.dev/ai-coding-dictionary/spec) before work is split into tickets. It adopts the perspective of an attacker with full internal knowledge of the system to identify race conditions, authorization bypasses, and business logic exploits.

The defining constraint is that it attacks the design before code is written and writes defensive constraints directly into the spec document rather than reviewing finished code. If a specification fails to consider malicious actors, [code-review](https://aihero.dev/skills-code-review) will approve vulnerable code because the implementation matches the incomplete specification.

## When to reach for it

You invoke this by typing `/red-team`. The [agent](https://www.aihero.dev/ai-coding-dictionary/agent) won't reach for it on its own.

| Situation | What to run |
| --- | --- |
| Finished a spec and about to break it into tickets | `/red-team` |
| Still grilling or discovering the core feature idea | [grill-with-docs](https://aihero.dev/skills-grill-with-docs) |
| Reviewing code changes that have already been implemented | [code-review](https://aihero.dev/skills-code-review) |
| Running an automated security check on a code diff | [security-audit](https://aihero.dev/skills-security-audit) |

## The attack vectors

The review attacks the specification across five primary vulnerabilities:

1. **Race conditions (TOCTOU)**: Parallel requests attempting to double-spend funds, reserve the same item, or exceed rate limits before the database commits state.
2. **Broken Object-Level Authorization (BOLA / IDOR)**: Querying or updating records by swapping IDs without verifying tenant or ownership context.
3. **Numeric manipulation**: Supplying negative quantities, floating-point rounding quirks, or integer overflow payloads to alter balances or prices.
4. **Denial of Wallet**: Unbounded pagination or unthrottled endpoints that invoke expensive external APIs or trigger database table scans.
5. **State machine smuggling**: Invoking workflow transitions out of sequence to skip verification or payment gates.

## Updating the spec

`red-team` does not produce an external report that gets disconnected from development. It modifies the specification file directly, appending a `Security Constraints & Threat Mitigations` block.

When [to-tickets](https://aihero.dev/skills-to-tickets) subsequently processes the spec, those security rules become explicit acceptance criteria in the resulting tickets, ensuring defensive logic is implemented and tested from the very first tracer bullet.

## Common questions

**Does every feature need a red-team pass?**
Purely visual updates or minor internal refactors do not require red teaming. However, any feature that mutates balances, handles authorization, interacts with external webhooks, or exposes public API endpoints benefits greatly from an adversarial pass.

**How does this differ from security-audit?**
`red-team` operates on specifications before implementation starts, focusing on conceptual business vulnerabilities. [security-audit](https://aihero.dev/skills-security-audit) operates on code diffs during review, checking actual syntax, database locks, DTO sanitization, and input schema validation.

## It's working if

- The spec gains a concrete `Security Constraints & Threat Mitigations` section.
- Concurrency, authorization, and rate limit rules are defined before tickets are generated.
- Tickets generated by [to-tickets](https://aihero.dev/skills-to-tickets) contain tests for adversarial edge cases.

## Where it fits

A user-invoked step placed directly between [to-spec](https://aihero.dev/skills-to-spec) and [to-tickets](https://aihero.dev/skills-to-tickets). It ensures specifications are hardened before tickets are scheduled. See [ask-matt](https://aihero.dev/skills-ask-matt) for the complete map of skills.
